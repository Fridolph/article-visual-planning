# 示例文章（中文）

标题：我把 OpenAI 官方三篇 Codex 指南读完了，整理成这一篇

平台：掘金 / 博客
读者：刚开始接触 Codex 的工程师与技术创作者
目标：把核心观点讲清楚，并帮助读者判断 Codex 在真实工作里怎么用

## 文章结构

### 引子

OpenAI 发布了三篇官方 Codex 指南。我把它们都读完后，整理成一篇更容易吸收的文章。核心结论很简单：把 Codex 当成一个可以持续配置和协作的队友，而不是偶尔用一下的工具。

### 第一部分：八个实用习惯

这一部分主要讲如何更好地使用 Codex：

- 提示词写清楚
- 复杂任务先用 Plan 模式
- 用 `AGENTS.md` 固化团队规则
- 让 Codex 自己跑测试、做 review
- 用 MCP 接入外部系统
- 把重复流程做成 Skill

其中有一节专门讲 Plan 模式。很多读者还没见过这个界面，所以真实截图会比纯文字更直观。

另一节介绍 `AGENTS.md`。这是全文最核心的概念之一，因为它决定了团队规范如何被沉淀和复用。

### 第二部分：Skills、Shell 与 Compaction

这一部分把三件事放在一起解释：

- Skills 负责保存可复用流程
- Shell 负责提供真实执行环境
- Compaction 负责避免长任务因为上下文过大而中断

这段内容强调的是三者之间的关系，而不是某一个具体界面。

### 第三部分：AI 如何参与软件开发全流程

这一部分依次讨论规划、设计、构建、测试、代码审查、文档和运维。

代码审查一节提到 Codex 可以审查每个 PR，还能发现竞态条件、硬编码等问题。如果能放一张真实 review 评论的截图，可信度会明显提高。

运维一节讨论基于 MCP 的日志分析。这个场景比较抽象，读者不一定能立刻想象“一个提示词同时串起日志、代码和 git 历史”到底是什么样。

### 结尾

最后收束到一个总原则：代理负责第一遍，工程师负责审查、判断和风险控制。
